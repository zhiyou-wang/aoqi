# 技术方案 · 奥奇传说精灵图鉴与养成系统

企业级实施的技术基线。定稿日期 2026-09-30。

## 定位

数据密集型图鉴/养成查询系统：Oracle 为数据底座，前端落地「冷色神迹工艺」设计系统，覆盖精灵、皮肤、技能、羁绊、关系、养成六大域的多维筛选、检索与详情展示。

数据规模：946 精灵 / 1334 皮肤 / 2689 技能 / 8381 技能等级 / 357 + 1635 羁绊 / 86 关系线。

## 技术栈

**原则：最少依赖 + 最高性能，面向低配置客户机。**

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端框架 | React 18 + TypeScript + Vite | 仅此两项运行时依赖（约 42KB gzip），组件化仍保留 |
| UI | 自研组件库（`aoqi-material` 封装成 React 组件） | 已有完整设计 token 与材质引擎 |
| 服务端状态 | 自研 `useFetch` hook | 替代 TanStack Query，只做请求+竞态取消，零依赖 |
| 路由 | 自研 hash 路由 | 替代 react-router-dom，仅两三个页面 |
| 客户端状态 | React 内置 `useState` | 替代 Zustand，UI 状态简单 |
| 虚拟滚动 | 自研（按需分批渲染） | 替代 TanStack Virtual，946 行可控 |
| 图表 | SVG 手写雷达图 | 替代 ECharts（约 350KB gzip），仅一处雷达图 |
| 后端 | FastAPI + oracledb + SQLAlchemy | 与 ETL 同语言；OpenAPI 内置 |
| 数据库 | Oracle（`scott`@`localhost:1521/orclpdb`） | 已有 `AOQI_*` schema |
| 工程化 | npm workspaces + ESLint + Prettier + Vitest/pytest | 统一管理 |
| 部署 | 本地 uvicorn + vite dev | 后续可 Docker Compose |

已砍掉的依赖（低配客户不背）：`react-router-dom`、`@tanstack/react-query`、`zustand`、`ECharts`、`TanStack Virtual`。前端运行时依赖仅 `react` + `react-dom`。

## 资源优化（背景图与图片）

背景图为《孙尚香-云端乐园》美宣图（原图 8K / 3.6MB），已压缩为多分辨率 WebP：

- 1920px ≈ 199KB（主背景）
- 1280px ≈ 102KB（中端）
- 960px ≈ 60KB（低端/弱网）

前端用 `<img srcset>` + `sizes="100vw"` 让浏览器按屏幕宽度自动选档，配合 `loading="lazy"` + `decoding="async"` + `fetchpriority="low"`，低配机器只加载所需分辨率。暖色图叠冷色压调层（`.aq-scene__tint`）保持低饱和冷色主视觉。

## 渲染架构（材质引擎的轻量化落地）

两篇文章（kube.io 的 Web 折射实现、Cocos 的 GPU 着色器实现）明确了关键结论：**渲染性能瓶颈在浏览器渲染管线，不在前后端语言**。

### 根本原则：渲染在客户端，计算可以前置

光学效果（液态玻璃、液态金属、色散、菲涅尔）是逐像素、逐帧、逐交互的实时渲染。渲染的输入是「用户此刻的屏幕 + 鼠标 + 滚动 + 动画帧」，每 16ms 更新一次，只能发生在客户端。若放后端即退化为云渲染（每个用户占 GPU、延迟 100ms+、成本是云游戏量级），不可行。

因此前后端分工如下：

| 是什么 | 放哪 | 理由 |
| --- | --- | --- |
| 位移向量场（超椭圆/晶体/长虹折射图） | **构建期离线预生成** | 形状固定，算一次缓存 PNG，前端零计算 |
| 法线图、噪声纹理、颗粒贴图 | **构建期离线预生成** | 静态资源 |
| 光学合成（位移图 + 色散 + 高光 → 背景） | **前端运行时** | 渲染本身，只能客户端 |
| 材质参数（折射率/色散强度/菲涅尔/各稀有度品级材质） | **后端下发配置** | 数据，可动态调 |
| 精灵/皮肤/羁绊业务数据 | **后端** | 业务数据 |

「各种形态」（超椭圆、圆形晶体、长虹锯齿、圆角矩形…）本质只是位移图不同，全部可离线预生成。前端运行时只做「选图 → 挂载 → 设 scale」，重数学（斯涅尔定律、向量场、射线模拟）在构建期就跑完了。

### 三种实现路径的代价

| 路径 | 执行位置 | 成本 | 适用规模 |
| --- | --- | --- | --- |
| CSS `backdrop-filter` | GPU 合成器 | 极低 | 946 张卡片全用 |
| SVG `feDisplacementMap` | CPU 光栅化 | 高，动态尺寸需重建位移图 | 每屏 <10 |
| WebGL2 离屏着色器 | GPU | 单 DrawCall 4 次采样完成折射+色散+高光 | 焦点对象 |

### 关键事实

1. **位移图可预计算 + 缓存**：折射沿边框对称，算一次、绕边框复用（kube.io 用 127 次射线模拟；Cocos 固化进贴图）。我们的形状固定是超椭圆 squircle，位移图可离线预生成一次、缓存成静态资产，运行时零计算。
2. **SVG 滤镜当 `backdrop-filter` 仅 Chromium 支持**，动态尺寸变化几乎每次都要全量重建位移图。
3. **GPU 方案性能碾压**：Cocos 单 DrawCall 内最多 4 次采样完成扭曲+色散+轮廓光，色散按需关闭采样。
4. **WebGL2 全浏览器支持**：若需在 Firefox/Safari 也上真折射，走 WebGL2 而非 SVG。

### 浏览器兼容性：能力检测 + 分级降级（功能不丢，效果精度不同）

```
能力检测 → 选择渲染路径

L2 高端（WebGL2，全浏览器）→ GPU 着色器：单 DrawCall 折射+色散+高光，可做大量玻璃
L1 中端（Chromium）        → 预计算位移图 + SVG feDisplacementMap
L0 兜底（所有浏览器）      → 纯 CSS backdrop-filter: blur() + 半透明
```

- `backdrop-filter: blur()` 已全主流浏览器支持，静态玻璃永远有保障。
- 只有「真折射」才需 Chromium/WebGL，降级到 L0 只少折射扭曲，玻璃质感、冷色、金属、布局、数据完全不受影响。
- 降级是运行时自动的，不改变业务逻辑。

### 前端臃肿的解法：材质引擎独立可裁剪 + 按需加载

- 材质引擎抽成 `frontend/src/components` 的独立模块，不塞进业务页面。
- 位移图等重资源是静态 PNG，不进 JS 体积。
- code splitting：材质引擎只在用到「焦点玻璃」的页面才加载，图鉴列表纯数据页不加载。
- 偶发动态计算（用户自定义形状）放 Web Worker，不阻塞主线程。

### 对 demo 代码的改造

`prototype/aoqi-material.js` 里的 `lens()` 目前为每个实例实时生成位移图。正式实施改为：

- 位移图由**离线脚本**（`backend/scripts/generate-displacement-map`）按「超椭圆 squircle / 圆形晶体 / 长虹锯齿」三类预生成 PNG，缓存为静态资产。
- 运行时只做「加载 PNG → 挂载 feImage → 设置 scale」，不重算位移场。
- 静态玻璃用 CSS 变量，不挂 SVG 滤镜。
- 材质引擎对外暴露 `AoqiMaterial` 统一入口，内部按能力自动选择 L0/L1/L2 路径。
